# VWorld 서울역 실내지도의 좌표·개체·텍스처 구조와 매장 데이터 결합 방안

- 조사 기준일: 2026-08-31
- 대상: VWorld `서울역KTX`, 사이트 ID `S202103`
- 목적: 기존 실내지도를 최신 매장으로 보완하고, 매장을 선택 가능한 개체로 만든 뒤 방문객·매출 데이터를 결합하는 방법을 결정한다.

## 먼저 결론

가능하다. 다만 VWorld 원본의 매장 사진을 직접 고치는 방식보다 다음과 같이 **기준 지도와 우리 업무 데이터를 분리**하는 것이 맞다.

1. VWorld `S202103` 3D Tiles는 건물·층·시설의 기준 공간으로 유지한다.
2. 우리 시스템에 `store_id`를 가진 매장 영역을 별도 등록한다.
3. 매장 영역에는 위치, 층, 바닥 폴리곤, 높이, 방향, 최신 이미지 또는 3D 모델을 넣는다.
4. 방문객·매출은 VWorld 내부 ID가 아니라 우리 `store_id`에 연결한다.
5. 화면에서 매장 영역을 클릭하면 강조, 정보창, 기간별 차트가 나타나게 한다.

이 구조가 필요한 이유는 화면에 보이는 매장 간판과 사진이 대부분 **영업점 데이터 레코드가 아니라 3D 표면에 붙인 사진 텍스처**이기 때문이다. 일부 시설은 독립 개체로 선택할 수 있지만, 매장 외관이 벽 또는 복합 모델에 합쳐져 있으면 원본만으로는 매장 하나를 안정적으로 선택할 수 없다.

## 1. 실내지도는 한 가지 데이터가 아니라 네 층으로 구성된다

| 층위 | 역할 | 서울역에서 확인된 형태 | 우리 시스템에서의 사용 |
|---|---|---|---|
| 구축 원본 규격 | 공간·시설의 기하와 속성을 작성·교환 | CityGML 2.0, IndoorGML 개념 | 원본 제작·갱신 기준을 이해하는 용도 |
| 웹 3D 표현 | 브라우저에 필요한 부분만 단계적으로 전송 | `tileset.json` + 571개 `b3dm` 타일 | VWorld 기준 배경, 층 표시, 일부 개체 선택 |
| 시설 POI | CCTV·에스컬레이터 같은 지점형 시설 검색 | `uid`, `fuid`, `puid`, `x`, `y`, `z` | 시설 마커, 길찾기, 설비 정보 |
| 매장 업무 레이어 | 최신 매장 영역과 경영지표 | 현재는 별도 구축 필요 | 선택, 모달, 방문객·매출·혼잡 시각화 |

한국의 [실내공간정보 구축 작업규정](https://www.law.go.kr/LSW/admRulInfoP.do?admRulSeq=2100000207410&chrClsCd=010201)은 위치정보, 기하정보, 속성정보, 텍스처 매핑을 각각 구분하고, 실내공간정보를 CityGML 2.0 데이터 형식과 IndoorGML 공간 개념으로 제작하는 것을 원칙으로 정한다. `LOD3`은 대상물을 촬영한 이미지를 3D 모델에 적용하는 단계다.

VWorld가 브라우저에 보내는 것은 이 구축 원본 전체가 아니라 렌더링에 맞게 변환한 [OGC 3D Tiles](https://docs.ogc.org/cs/18-053r2/18-053r2.html)다. 따라서 VWorld 화면에 보이는 필드만 보고 원본 CityGML 속성이 전부 공개됐다고 보면 안 된다.

### 공식 구축 원본의 표준 속성

작업규정 별표 6의 `실내공간정보 속성입력`에는 원본 공간·시설 개체에 다음과 같은 공통 필드가 정의돼 있다.

| 컬럼 ID | 길이 | 의미 |
|---|---:|---|
| `PRIMARYKEY` | 41 | 기본키 |
| `FOREIGNKEY` | 38 | 연결되는 3차원 객체 코드 |
| `LAYER` | 35 | 레이어 코드 |
| `ID` | 17 | UFID, 공간객체 등록번호 |
| `FLOOR` | 6 | 층 |
| `DIVISION` | 2 | 이동·안내·편의·운수·안전·소방·판매·의료·관리·구조 등의 구분 |
| `CLASSIFY` | 2 | 공간·시설물·천정·벽·바닥·문·창문·기둥 등의 구조 분류 |
| `KIND` / `KINDENG` | 50 / 100 | 세부항목 한글·영문 |
| `SERIAL` | 5 | 일련번호 |
| `NAME` | 50 | 명칭 |
| `QUAL` | 6 | 재질 |
| `SLP` | 6 | 경사 |
| `DIR` | 6 | 진행 방향 |
| `SKT` | 6 | 내·외부 |
| `HANDICAP` | 6 | 교통약자 구분 |
| `FPOINT` / `SPOINT` | 36 / 36 | 경로연결 시작점·끝점의 기본키 |

즉 국가 구축규격 자체는 매장과 시설을 `층 + 구조 분류 + 세부항목 + 명칭 + UFID`로 객체화할 수 있게 설계돼 있다. 문제는 VWorld 웹 서비스가 이 전체 속성 테이블을 그대로 공개하지 않고, 렌더링용 3D Tiles에서는 `FLOOR`, `TD_ID`, `MODEL_NAME`, `__OID__` 등 일부만 제공한다는 점이다.

## 2. 서울역 S202103에서 실제로 확인한 구조

### 2.1 사이트와 층

VWorld 서비스 응답의 서울역 기본 단위는 다음과 같다.

```json
{
  "uid": "S202103",
  "kname": "서울역KTX",
  "x": "126.97082",
  "y": "37.55363",
  "z": "27.2"
}
```

층에는 사이트 ID와 층명이 결합된 별도 ID가 있다.

| 층 | 층 ID `fuid` | 관찰된 기준 높이 `z` |
|---|---|---:|
| B7 | `S202103B7` | -18.3 |
| B6 | `S202103B6` | -10.7 |
| B3 | `S202103B3` | 7.5 |
| B2 | `S202103B2` | 14.0 |
| B1 | `S202103B1` | 25.9 |
| 1F | `S2021031F` | 30.1 |
| 2F | `S2021032F` | 38.1 |
| 3F | `S2021033F` | 44.2 |
| 4F | `S2021034F` | 50.0 |
| RF | `S202103RF` | 52.9 |

VWorld 화면도 `FLOOR` 속성에 스타일 조건을 적용해 선택한 층 외의 개체를 숨긴다. 현재 프로젝트 역시 [app.js](/Users/hoonsbook/Documents/ChatGPT/DigitalTwin_Station/app/app.js:365)에서 같은 방식으로 층을 필터링한다.

### 2.2 시설 POI

시설 검색 응답에서 확인한 필드는 다음과 같다.

```json
{
  "uid": "S202103",
  "fuid": "S2021032F",
  "fname": "2F",
  "puid": "INPU_000000000074958",
  "pnam": "에스컬레이터",
  "pdes": "",
  "x": "126.971276355255370",
  "y": "37.554481444167934",
  "z": "37.77",
  "d": "0.000000000000000"
}
```

`x`, `y`는 서울역에 대응하는 경도·위도 값이며, `z`는 해당 시설의 높이 값이다. 2층 `에스컬레이터` 검색에서는 7개 POI가 조회됐다. 반면 `맥도날드` 검색은 0건이었다.

여기서 확인되는 사실은 다음과 같다.

- **사실:** CCTV, 에스컬레이터 등은 `puid`가 있는 별도 시설 POI다.
- **사실:** 시설 POI에는 사이트, 층, 경도, 위도, 높이가 있다.
- **관찰에 근거한 추론:** 화면에 보이는 매장 간판과 파사드가 같은 POI 목록에서 검색되지 않으므로, 매장 사진은 시설 POI와 별개의 3D 텍스처일 가능성이 높다.
- **주의:** 이 POST 응답은 현재 VWorld 화면이 사용하는 서비스 구현이다. 공개 개발자 문서에서 안정성이 보장된 OpenAPI 계약은 확인하지 못했다.

### 2.3 3D Tiles와 개체 속성

서울역 3D Tiles 루트에는 다음 속성명이 선언돼 있다.

```json
{
  "properties": {
    "FLOOR": {},
    "SITE": {},
    "TYPE": {},
    "TD_ID": {},
    "MODEL_NAME": {},
    "__OID__": {}
  }
}
```

샘플 `b3dm` 타일의 개별 피처에는 다음 값이 들어 있었다.

```json
{
  "FLOOR": ["B3"],
  "SITE": ["서울역KTX"],
  "TYPE": [null],
  "TD_ID": ["b00540045882100332203369700"],
  "MODEL_NAME": ["B03FC020"],
  "__OID__": [426]
}
```

타일 내부 GLB의 메시에는 `_BATCHID`가 있어 화면에서 선택된 삼각형을 위 속성 레코드와 연결할 수 있다. OGC 3D Tiles 표준도 피처를 런타임에 선택하고 Batch Table 속성을 조회해 시각화·분석에 사용할 수 있도록 정의한다.

다만 `TD_ID`, `MODEL_NAME`, `__OID__`가 VWorld 재측량이나 타일 재생성 뒤에도 유지된다는 공개 보장은 확인하지 못했다. 따라서 이 값들은 `source_feature_id`로 보존하되, 매출을 연결하는 영구 기본키로 쓰면 안 된다.

### 2.4 서울돈까스 파사드의 실물 추출 확인

현재 화면에서 매장군을 덮는 부모 타일 `B_0_20_16`, `B_0_24_16`은 `REPLACE` 방식이며, 가까이 이동하면 각각 4개의 상세 자식 타일 `B_1_*`로 교체된다. 이 8개 자식 타일을 수집해 `b3dm → GLB → 이미지` 순서로 분리한 결과, 서울돈까스 파사드 원본을 다음 위치에서 확인했다.

| 항목 | 확인값 |
|---|---|
| 상세 타일 | `B_1_25_17.b3dm` |
| GLB 내부 이미지 | `image-02.jpg` |
| 이미지 규격 | JPEG, 512×512, sRGB |
| 이미지 SHA-256 | `3bef2cab207e18a9188812b764d9504ce63234704f54d9e3af72d37c3166c881` |
| 재질 연결 | `material 1 → texture 1 → image 2` |
| 같은 타일의 2F 피처 | `F02FC087`, `F02WL037` |
| 파사드와 연결되는 것으로 판단되는 피처 | `F02WL037` (`WL`: wall) |
| 참고 원본 ID | `TD_ID=b00540045882300332205496100`, `__OID__=928` |

따라서 화면의 `서울돈까스`는 HTML에 별도로 올린 사진이나 POI 아이콘이 아니라, 상세 3D 타일의 벽 메시 재질에 붙은 실사 JPEG 텍스처다. 정확한 표현은 **“LOD3 모델에 매핑된 파사드 텍스처”**다. LOD3은 이미지 파일의 종류가 아니라 모델의 세밀도·구축 단계이고, 실제 웹 전달 단계에서는 이 사례처럼 JPEG 또는 KTX2가 GLB 안에 포함된다.

이 사례는 파사드 이미지를 추출할 수 있다는 점과 동시에 한계를 보여준다. 텍스처 파일은 분리할 수 있지만, 그것만으로 매장 바닥 영역·상호·영업 이력까지 갖춘 업무 개체가 만들어지는 것은 아니다. `타일 → 메시/재질 → 원본 피처 → 우리 store_id` 연결표를 추가로 관리해야 한다.

## 3. 좌표는 어떤 식으로 구성되는가

### 외부 위치 표현

- 시설 POI의 `x`, `y`: 경도·위도 형태의 십진수 좌표
- 시설 POI의 `z`: 층·시설 높이
- 층과 시설을 묶는 키: `uid` → `fuid` → `puid`

### 3D Tiles의 공간 표현

`tileset.json`의 `boundingVolume.region`은 다음 순서다.

```text
[west, south, east, north, minimumHeight, maximumHeight]
```

경도·위도는 WGS84(EPSG:4979)의 라디안, 높이는 WGS84 타원체 기준 미터다. 서울역 루트 영역을 도(degree)로 환산하면 대략 다음 범위다.

```text
서 126.9691617 / 남 37.5513145
동 126.9732475 / 북 37.5577269
높이 -24.57m ~ 58.61m
```

각 `b3dm`은 `RTC_CENTER`라는 지구중심좌표(ECEF) 기준점과 그 주변의 로컬 정점 좌표를 함께 사용한다. 애플리케이션에서 이를 직접 계산할 필요는 거의 없다. Cesium이 타일을 배치하고, 우리 업무 레이어는 다음 두 방식 중 하나로 올리면 된다.

1. 경도·위도·높이를 `Cartesian3.fromDegrees`로 변환한다.
2. 서울역 기준점에서 동(East)·북(North)·상(Up) 미터 단위의 로컬 ENU 좌표를 사용한다.

현재 프로젝트는 두 번째 방식을 이미 사용한다. [app.js](/Users/hoonsbook/Documents/ChatGPT/DigitalTwin_Station/app/app.js:265)에서 서울역 기준 ENU 프레임을 만들고, [app.js](/Users/hoonsbook/Documents/ChatGPT/DigitalTwin_Station/app/app.js:601)에서 사용자가 찍은 3D 지점을 다시 ENU 좌표로 변환한다.

### 정확도를 높이는 실무 방식

매장마다 화면을 보며 감으로 좌표를 맞추는 대신, 층별로 다음 과정을 거치는 편이 좋다.

1. 에스컬레이터 모서리, 기둥 중심, 출입구처럼 변하지 않는 기준점 3개 이상을 잡는다.
2. 도면 또는 현장 실측점과 VWorld상의 동일 지점을 대응시킨다.
3. 층별 평행이동·회전·축척 변환값을 계산한다.
4. 매장 바닥 외곽을 폴리곤으로 그린다.
5. 화면 표시용 중심점과 높이는 폴리곤에서 파생한다.

이렇게 하면 매장 하나를 직육면체로 맞추는 작업과 전체 층 정합 작업을 분리할 수 있다.

## 4. 기존 매장 사진은 무엇이며, 교체할 수 있는가

### 확인된 사실

실내공간정보 구축 규정의 LOD3은 시설물을 실제 높이로 3D 모델링하고, 대상물을 촬영한 이미지를 가시화 정보로 사용한다. 서울역 GLB에서도 JPEG·PNG·KTX2 이미지가 확인됐고, 실제 매장 파사드 사진이 3D 표면에 붙어 있었다.

### 의미

매장 간판이나 정면 사진은 보통 다음 중 하나다.

- 독립된 매장 모델에 붙은 텍스처
- 벽·매장군처럼 여러 대상을 합친 모델에 붙은 텍스처

첫 번째이면 해당 피처를 선택하고 스타일을 바꿀 여지가 있다. 두 번째이면 매장 사진 한 장만 떼어 선택하거나 교체하기 어렵다. 원본 `b3dm`과 GLB를 재가공해야 하고, VWorld CDN 원본을 직접 수정할 수도 없다.

### 권고

기존 텍스처를 해킹하듯 바꾸지 말고, 우리 소유의 다음 레이어를 위에 올린다.

- 클릭용 투명 바닥 폴리곤 또는 얇은 박스
- 필요 시 기존 파사드를 가리는 최신 파사드 평면
- 고품질 매장은 별도 GLB 모델
- `store_id`가 포함된 선택 메타데이터

원본 개체가 별도 피처일 때는 VWorld 피처의 표시를 조건부로 숨기는 방법도 검토할 수 있지만, 장기적으로는 원본 피처 ID의 안정성과 이용권한을 먼저 확인해야 한다.

## 5. 권장 매장 데이터 모델

### `station_site`

| 필드 | 예시 | 용도 |
|---|---|---|
| `site_id` | `S202103` | VWorld 사이트 연결 |
| `name` | `서울역KTX` | 역사명 |
| `origin_lon`, `origin_lat`, `origin_h` | 서울역 기준점 | ENU 변환 기준 |

## 6. 클릭과 시각화는 이렇게 연결된다

```text
사용자 클릭
  ├─ VWorld 3D 피처 → TD_ID / MODEL_NAME / __OID__ 확인
  └─ 우리 매장 오버레이 → store_id 확인
                         ↓
              매장 마스터·최신 자산 조회
                         ↓
      방문객 / 매출 / 체류시간 / 혼잡 시계열 조회
                         ↓
     강조 외곽선 + 정보 모달 + 막대·선 그래프 표시
```

우리 매장 레이어는 클릭 우선순위를 VWorld 원본보다 높게 두면 된다. 매장 선택 시 다음을 동시에 표현할 수 있다.

- 바닥 영역과 외벽 강조
- 매장명, 영업상태, 최신 확인일
- 방문객과 매출의 현재값
- 시간대별 막대그래프 또는 추세선
- 매장 주변 유동인구 히트맵
- `출입자 → 방문자 → 결제자` 전환 퍼널

## 8. 확인된 사실, 추론, 미확인 사항

### 확인된 사실

- VWorld 서울역KTX 사이트 ID는 `S202103`이다.
- 실제 웹 3D는 3D Tiles와 `b3dm`을 사용한다.
- 타일 피처에는 `FLOOR`, `SITE`, `TD_ID`, `MODEL_NAME`, `__OID__`가 있다.
- 시설 POI는 `uid`, `fuid`, `puid`, `x`, `y`, `z`를 가진다.
- 층 표시는 `FLOOR` 속성 필터로 제어된다.
- LOD3 규정은 현장 촬영 이미지의 텍스처 매핑을 요구한다.
- 실제 서울역 GLB에서 사진 텍스처와 `_BATCHID`가 확인됐다.

### 추론

- 기존 매장 외관은 조사 시점의 LOD3 텍스처일 가능성이 높다.
- 매장명 검색이 되지 않는 외관은 독립 POI로 관리되지 않을 가능성이 높다.
- VWorld 개체 ID는 내부 갱신 때 바뀔 수 있으므로 사내 영구키로 부적합할 가능성이 있다.

### 아직 확인이 필요한 사항

- VWorld가 `indoorServices.do`, `indoorFloor.do`를 외부 개발용 공식 API로 보장하는지
- `TD_ID`, `MODEL_NAME`, `__OID__`의 버전 간 안정성
- 원본 타일·사진 텍스처의 경진대회 및 상업 서비스 재사용 범위
- 시설 POI `z`의 정확한 수직 기준과 층별 오차
- 서울역 원본 CityGML 또는 IndoorGML의 별도 제공·갱신 절차
